## Production ownership and scheduling

- After a successful final preview, the existing detached preparation task prepares
  bounded CPU input caches, then attempts preparation on an already-created GPU.
- The scheduler retains an `Arc<GpuRenderer>`; it still serializes actual renders
  through the existing recoverable GPU boundary. Preparation takes only a short
  `try_lock` to clone that Arc, then releases the scheduler lock before compilation.
- Spatial/denoise stage construction happens outside their stage locks. Publication
  uses `try_lock` and preserves a foreground winner. No render waits for a background
  stage lock. Driver-internal contention is still possible and needs measurement.
- One atomic preparation guard bounds concurrent preparation per renderer. Request
  epochs are checked before and after each construction; observed superseded work
  is discarded. These pipelines contain no photo/edit identity. Already-entered
  driver compilation cannot be cancelled.
- No new device, pixel buffer, upload, dispatch, readback, image frame or edit is
  generated by preparation. Source identities and preview/export math are unchanged.
- Optional preparation failure is retained in scheduler diagnostics. Normal rendering
  retains its typed GPU failure and explicitly labelled Native CPU fallback boundary.

## Evidence and limitations

21 render GPU tests passed, including 75 cold and 75 prepared CPU-reference cases,
HDR, alpha, borders, cached repeat and pipeline/buffer counts. Deterministic lock
tests prove preparation holds no stage lock during construction, does not replace
foreground winners, and discards stale work. Four desktop GPU boundary tests pass.
Targeted desktop warning-denied Clippy and script ESLint pass. The atomic statistics
read and explicit CPU-preference guard are included in subsequent full acceptance.

The real Native benchmark separately records idle preparation cost and request
latency; preparation is not free work and must never be hidden in the report.
The production command does not await it. Benchmarking completed preparation is
not evidence that every user gesture will occur after preparation has completed.
Whole-UI pointer-to-present, live contention, heavy-combination latency, initial
RAW open/1:1, large-image qualification and installed application remain open.
No new installer has been produced. Original Phases0–30 remain required.
