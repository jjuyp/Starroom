# Bounded display histogram counting cost

2026-11-09. Phase16 component improvement, not whole-UI acceptance.

The RGB display histogram previously created/invoked a forEach callback for
every sampled preview pixel. The production loop now updates the three count
arrays directly, with identical channel bins, stride, alpha policy, global
channel normalization and separate unchanged luminance calculation.
No new color/image processing: this analyzes already-rendered display bytes only.
No sampling reduction, input mutation, extra readback, new dependency or license.

## Evidence

- Frozen prior callback implementation versus production loop at full
  512/1024/2048 tier dimensions, bins4/48/128, including transparent bytes and
  the existing stride: exact array equality. Existing channel/immutability and
  Native payload ownership/readback tests remain.
- Real Native SRP4 frame1024x680 via production parser and
  scripts/fixtures/histogram-count-browser.mjs; isolated HeadlessChrome156.
  Alternating old/new32 rounds,2 warmups excluded from timing, all32 histogram
  comparisons exact. Median7.10->5.25ms; p958.30->6.10ms.
  Full native tests and other benchmarks had completed before this measurement.
- Full Web1794228773739:237 tests/34files, ESLint, TypeScript, production build,
  JSON/Golden/RAW manifests and packaging configuration all exit0.

Reproduction: bundle the fixture module with existing Rolldown as IIFE
StarroomHistogramProbe and call verifyHistogramCounting with an actual SRP4 RGBA
ArrayBuffer generated by preview_transport_probe. It throws if channel/luminance
results change and returns each measured sample.

These are CPU counting timings only, not IPC, decode/draw, OS presentation or an
installed application response-time claim. Do not add these independent
measurements to other benchmark medians to claim an end-to-end speed.
